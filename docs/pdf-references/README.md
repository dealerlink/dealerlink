# PDF reference captures — the F.38 diff target

These are **known-good PDFs rendered by the CURRENT Chromium pipeline**. They
exist so Day 26's Typst templates have something concrete to diff against, and
so Day 27 has snapshot targets. Nothing here is generated by Typst.

## How they were produced

|                 |                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------- |
| Commit          | `b4fd549` (branch `day-25-typst-spike`, cut from `main`)                                  |
| Seed            | `pnpm db:seed` at that commit — base + day5/6/7/8/11/12/13                                |
| Renderer        | `apps/workers/scripts/capture-references.ts`                                              |
| Capture command | `cd apps/workers && pnpm exec tsx scripts/capture-references.ts --manifest <matrix.json>` |

The capture script calls the **same** builders (`buildQuotationHtml`,
`buildPerformaInvoiceHtml`, `buildPaymentReceiptHtml`, `buildDispatchNoteHtml`)
and the **same** `renderPdfFromHtml` that `runRenderPdf` uses in production. It
differs from production in exactly one way: it writes the buffer to disk instead
of persisting a `generated_documents` row, so capture does not mutate tenant
data.

### WHICH BINARY RENDERED THESE — read this before trusting a diff

**These were rendered by the arm64 Chromium that Playwright installs
(`~/.cache/ms-playwright/chromium-1217/chrome-linux/chrome`), not by the
`@sparticuz/chromium` binary production uses.** That is forced by DEV.89: on this
arm64 devcontainer the `@sparticuz` binary is x86-64 and cannot launch. The exact
path and `process.arch` are recorded per-run in `capture-results.json`.

For the purpose these serve — _is the Typst output correct?_ — this is fine:
a reference only needs to be right, not to have been produced by the production
binary. But **if a Day 26 Typst render disagrees with a reference, the reference
itself is a suspect**, and the first question to ask is whether the two Chromium
builds lay the document out identically. Do not treat a mismatch as a Typst bug
without eliminating that.

**Two gaps, stated rather than papered over.** Both are matrix cells the seeded
data does not produce, and both need a decision before Day 26 leans on them:

- **Branded tenant.** `tenant_settings.logo_url` is NULL on both `demo` and
  `sample`, so every reference here is the unbranded path. Bank details ARE
  present and DO render. Closing this needs a logo set on a tenant and a
  re-capture; it is the one visual surface the Day 26 sign-off gate most needs.
- **Round-off.** No captured document renders a round-off line. Either the seed
  produces no total that needs one, or the templates do not emit the line —
  **that distinction is not yet established and should not be assumed.** The
  round-off rule is CLAUDE.md §5 ("applied at grand total, not per line"), so it
  matters; F.38's guardrail is that no number on any document may change.

## The long-serial fixtures

Seeded dispatches top out at **8** serials, so the matrix's highest-risk case is
built by `apps/workers/scripts/long-serial-fixture.sql`:

```
psql "$DATABASE_DIRECT_URL" -v ON_ERROR_STOP=1 -f apps/workers/scripts/long-serial-fixture.sql
```

It creates `DSP-REF-0026` and `DSP-REF-0500` on the `demo` tenant, with their own
dedicated inventory (`REF-SN-00001` … `REF-SN-00526`) so no seeded stock is
consumed or mutated. It is **idempotent** (it deletes its own rows first) and
**throwaway** — `pnpm db:seed` truncates, which is how the dev database is
returned to its seeded state afterwards.

**Verified in the captured output, not assumed:** the dispatch note renders every
serial individually — 26 on one page, and all 500 across two pages, each unique,
none dropped.

## Acceptance targets for Day 26

`reference-metadata.json` records, per reference: page count, byte size, the
count of ₹ (U+20B9) glyphs surviving text extraction, and the extracted tax
summary / totals / amount-in-words text. **Those values are the acceptance
target, independent of pixel layout** — Day 26 should match the numbers and the
text, then the Day 26 sign-off gate covers the visual.

Note `₹` appears **1–2 times per document** in the Chromium baseline and survives
extraction. Typst must match that; the spike confirms it can (`docs/TYPST_SPIKE.md`).

## Known limitation of the capture script

`apps/workers/scripts/capture-references.ts` is **not covered by
`pnpm typecheck`**. `apps/workers/tsconfig.json` sets `include: ["src"]` and
`rootDir: "src"`, so a script outside `src/` cannot be added to that project
without changing the build's output shape — which is not a change worth making
for capture tooling. It is lint-clean (`pnpm exec eslint`) and is exercised by
being run, but a type error in it would not be caught by CI. If this script
grows, give it its own `tsconfig.json` with `noEmit` rather than widening the
build's `rootDir`.
